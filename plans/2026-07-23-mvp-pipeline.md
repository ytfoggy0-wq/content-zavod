## Проект

Путь: `C:\Users\ytfog\OneDrive\Desktop\content-zavod\`

Что это: портфолио-проект — система, которая собирает данные о Reels 50 Instagram-конкурентов,

## Контекст

Ресёрч (проведён в этом же чате ранее, зафиксирован в `research/research-plan-content-zavod-2026-07-23.md`
и итоговом сообщении агента) дал следующие принятые решения:

1. **Сбор данных Instagram** — сервис **Apify** (пользователь изначально называл его «epify» — это
   опечатка/спутанное название, подтверждено пользователем в этом чате, что имелся в виду Apify).
   У Apify есть бесплатные кредиты новому пользователю без привязки карты. Ориентировочная цена —
   около $2.6 за 1000 результатов (нужно проверить точную цифру и текущие условия при регистрации,
   см. Задачу 0). Бесплатных кредитов хватит на разовый прогон, не на постоянный ежедневный мониторинг —
   закладывать это в ожидания.
2. **Транскрибация** — **Groq API**, модель Whisper (`whisper-large-v3` или актуальный аналог на
   момент реализации), бесплатный tier. Лимиты free tier могут быть небольшими — собирать пачками,
   не гнать все ролики разом (см. Задачу 3).
3. **Хранение данных** — **Supabase (Postgres)**. Выбран вместо Airtable, потому что проект — учебный
   кодовый портфолио-проект (должен быть код, а не no-code конструктор), и вместо голого Google Sheets —
   потому что даёт настоящую реляционную БД с возможностью расти дальше.
4. **Витрина данных (MVP)** — встроенный **Supabase Table Editor** (готовая сортировка/фильтрация
   «из коробки», без кода). Кастомный веб-фронтенд — не в этом ТЗ, это следующий шаг после MVP
   (см. «Открытые вопросы»).
5. **Метрика успешности ролика**:
   ```
   score = views / median(views за последние N роликов этого же аккаунта)
   ```
   Медиана взята вместо среднего, потому что устойчива к выбросам (один вирусный ролик не должен
   искажать оценку «нормы» аккаунта). `N = 20` (последние 20 роликов аккаунта, не считая текущий).
   Если у аккаунта меньше 20 роликов в базе — считать медиану по тому, что есть, но не менее 5 роликов
   (иначе `score` не считать, оставить `NULL`).
6. Юридический риск: скрапинг публичных данных через Apify — приемлемо (не логин в личный аккаунт).
   Дословное копирование сценариев конкурентов — не задача системы; система показывает идею, а не
   инструмент автогенерации копий. Это не блокирует реализацию, просто фиксируется как понимание цели.

Apify actor (конкретный «скрапер» в маркетплейсе Apify) для Reels ещё не выбран и не протестирован —
это первая практическая задача (см. Задача 0), потому что от точных полей в ответе actor'а зависит
схема таблицы `reels`.

## Цель

К концу этого ТЗ должно работать (проверяется вручную, см. «Как проверить»):

1. Список из (для MVP — **5**, не 50) Instagram-аккаунтов конкурентов, заданный в конфиг-файле.
2. Скрипт, который через Apify забирает последние N Reels каждого аккаунта (views, likes, дата,
   ссылка, длительность, подпись/caption) и сохраняет их в таблицу `reels` в Supabase.
3. Скрипт, который для роликов без транскрибации скачивает аудио и прогоняет через Groq Whisper,
   записывая текст обратно в `reels.transcript`.
4. Скрипт/SQL-функция, которая пересчитывает `reels.median_score` по формуле из Контекста.
5. Открыв Supabase Table Editor, можно отсортировать таблицу `reels` по `median_score` по убыванию
   и увидеть для каждого ролика: название аккаунта, дату, ссылку, транскрибацию, score.

MVP сознательно ограничен 5 аккаунтами вместо 50 — чтобы проверить весь пайплайн end-to-end дёшево
и быстро на бесплатных лимитах, прежде чем масштабировать на все 50 (масштабирование — отдельный
следующий шаг, не в этом ТЗ).

### Задача 1 — Схема БД в Supabase

Создать в Supabase (через SQL Editor в веб-интерфейсе Supabase) две таблицы:

```sql
create table accounts (
    id bigint generated always as identity primary key,
    username text unique not null,
    added_at timestamptz default now()
);

create table reels (
    id bigint generated always as identity primary key,
    account_id bigint references accounts(id) not null,
    url text unique not null,
    caption text,
    posted_at timestamptz,
    views bigint,
    likes bigint,
    duration_seconds numeric,
    transcript text,
    median_score numeric,
    collected_at timestamptz default now()
);

create index on reels (account_id);
create index on reels (median_score desc);
```

Названия колонок `caption`, `views`, `likes`, `duration_seconds` — адаптировать под реальные поля
из ответа Apify actor'а (см. Задача 0), сохранив типы и смысл. `median_score` заполняется отдельным
шагом (Задача 4), при вставке ролика оставлять `NULL`.

### Задача 2 — Скрипт сбора данных через Apify

Файл: `content-zavod/src/collect_reels.py` (Python 3.11+).

**Вход:** список username-ов конкурентов — вынести в `content-zavod/config/accounts.txt`,
по одному username на строку (для MVP — 5 строк).

**Логика:**
1. Прочитать `config/accounts.txt`.
2. Для каждого username:
   - Если аккаунта нет в таблице `accounts` — вставить (`insert ... on conflict (username) do nothing`).
   - Вызвать Apify actor через официальный Python-клиент `apify-client` (`pip install apify-client`),
     передав username и лимит (например, последние 20 Reels).
   - Дождаться завершения запуска actor'а (`run_sync` или polling через клиент — использовать
     синхронный метод клиента, не писать собственный poll-цикл).
   - Получить датасет результатов (`client.dataset(dataset_id).list_items()`).
3. Для каждого ролика в результате:
   - Если `url` уже есть в таблице `reels` (проверить перед вставкой либо использовать
     `on conflict (url) do update` на изменяемые поля `views`, `likes`) — обновить `views`/`likes`
     (просмотры растут со временем, это ожидаемо), не трогать `transcript`.
   - Если `url` новый — вставить строку с `account_id`, `url`, `caption`, `posted_at`, `views`,
     `likes`, `duration_seconds`; `transcript` и `median_score` оставить `NULL`.
4. Использовать `supabase-py` (`pip install supabase`) для работы с Supabase, коннект через
   `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` из `.env` (грузить через `python-dotenv`).
5. Вывести в консоль краткий отчёт: сколько аккаунтов обработано, сколько новых роликов добавлено,
   сколько обновлено.

**Ограничение по времени/лимитам:** обрабатывать аккаунты по одному, с паузой 2-3 секунды между
запусками actor'а (не слать все 5 запросов параллельно) — экономия кредитов Apify и защита от
лимитов.

### Задача 3 — Скрипт транскрибации через Groq Whisper

Файл: `content-zavod/src/transcribe_reels.py`.

**Логика:**
1. Выбрать из таблицы `reels` строки, где `transcript is null` и `url is not null`, лимит —
   например, 10 роликов за один запуск скрипта (не гнать всё сразу, беречь бесплатный лимит Groq).
2. Для каждого ролика:
   - Скачать видео по `url` (сам ролик или прямую ссылку на видеофайл, если Apify actor уже
     возвращает `videoUrl` — использовать её напрямую, не парсить HTML-страницу Instagram заново).
   - Извлечь аудиодорожку через `ffmpeg` (должен быть установлен в системе;
     команда вида `ffmpeg -i input.mp4 -vn -acodec mp3 output.mp3`, вызывать через `subprocess`).
   - Отправить `output.mp3` в Groq API (`groq` python-пакет, `pip install groq`),
     модель `whisper-large-v3`, метод `client.audio.transcriptions.create(...)`.
   - Записать полученный текст в `reels.transcript` для этой строки (`update ... where id = ...`).
   - Удалить временные файлы (видео и mp3) после обработки — не хранить их локально.
3. Между запросами к Groq — пауза 1-2 секунды.
4. Вывести в консоль отчёт: сколько роликов транскрибировано, сколько ошибок (с текстом ошибки,
   не молча пропускать).

**Важная проверка перед этой задачей:** если в Задаче 0 выяснится, что выбранный Apify actor уже
возвращает готовый transcript ролика в составе ответа — эта задача (3) не нужна, поле `transcript`
заполняется сразу в Задаче 2 из ответа actor'а. Решение зафиксировать по факту теста Apify actor'а.

### Задача 4 — Расчёт метрики median_score

Файл: `content-zavod/src/calc_scores.py`.

**Логика:**
1. Для каждого `account_id` из таблицы `accounts`:
   - Выбрать все `views` этого аккаунта, отсортированные по `posted_at` убывающе.
   - Для каждого ролика посчитать медиану `views` по **предыдущим** (более старым, не считая сам
     ролик) роликам того же аккаунта — брать не более последних 20 таких роликов.
   - Если предыдущих роликов меньше 5 — оставить `median_score = NULL` для этого ролика.
   - Иначе: `median_score = views этого ролика / медиана(views предыдущих N роликов)`, округлить
     до 2 знаков после запятой.
   - Записать `median_score` в таблицу `reels` (`update`).
2. Использовать `numpy.median` или `statistics.median` для расчёта — не писать вычисление медианы
   вручную.
3. Скрипт можно (и нужно) запускать повторно после каждого нового сбора данных (Задача 2) —
   он пересчитывает `median_score` для всех роликов заново, это недорого при 5 аккаунтах.

## Что НЕ менять

- **Не строить кастомный веб-фронтенд в этом ТЗ.** Витрина на MVP — встроенный Supabase Table
  Editor. Свой фронтенд (например на Streamlit) — отдельная задача после проверки, что данные
  и метрика вообще корректны на реальных 5 аккаунтах.
- **Не увеличивать список конкурентов до 50 в рамках этого ТЗ.** Сначала 5 аккаунтов сквозь весь
  пайплайн, потом отдельным шагом — масштабирование (оно упирается в лимиты Apify/Groq, требует
  отдельного решения о батчинге и расписании).
- **Не логиниться в личный Instagram-аккаунт ни через один скрипт.** Весь сбор данных — только
  через Apify actor на публичных данных, без логина — это осознанное решение по риску бана
  (см. Контекст, п.6).
- **Не хранить секреты (Apify token, Groq key, Supabase service_role key) в коде или в git.**
  Только `.env`, добавленный в `.gitignore`.

## Порядок реализации

1. **Задача 0** — сначала: без реального ответа Apify actor'а нельзя зафиксировать точную схему
   таблицы `reels` (Задача 1) и логику скриптов (Задачи 2-3).
2. **Задача 1** — сразу после Задачи 0, схема БД нужна всем следующим скриптам.
3. **Задача 2** — сбор данных, зависит от готовой схемы (Задача 1).
4. **Задача 3** — транскрибация, работает по данным из Задачи 2 (нужны строки с `url`/`videoUrl`

   принимается по факту Задачи 0.
5. **Задача 4** — расчёт метрики, нужны реальные `views` из Задачи 2, может выполняться независимо
   от готовности Задачи 3 (транскрибация и метрика друг от друга не зависят).

## Как проверить

Пошагово, вручную (кода с тестами в MVP нет — это разовые скрипты, не сервис):

```bash
cd content-zavod
python -m venv venv
source venv/Scripts/activate   # Windows Git Bash; на PowerShell: venv\Scripts\Activate.ps1
pip install apify-client supabase groq python-dotenv numpy

# 1. Собрать данные
python src/collect_reels.py
# Ожидаемо: в консоли — «Обработано аккаунтов: 5, новых роликов: N, обновлено: M»

# 2. Транскрибировать (если Задача 3 актуальна)
python src/transcribe_reels.py
# Ожидаемо: «Транскрибировано: K, ошибок: 0» (или с текстом ошибок, если есть)

# 3. Посчитать метрику
python src/calc_scores.py
# Ожидаемо: «Обновлено median_score для N роликов»
```

Затем открыть Supabase → Table Editor → таблица `reels` → отсортировать по `median_score`
по убыванию (клик по заголовку столбца). Ожидаемо: наверху — ролики с самым высоким соотношением
просмотров к медиане своего аккаунта; у каждой строки видны `url` (кликабельно открыть оригинал),
`caption`, `posted_at`, `transcript`, `median_score`.

Признак готовности MVP: для всех 5 тестовых аккаунтов в таблице есть ролики с непустым
`transcript` и не-NULL `median_score` минимум у части строк (у самых новых роликов, где меньше
5 предыдущих, `median_score` ожидаемо `NULL` — это нормально, не баг).
